# S1.3 — the layout shell and the theme toggle, verified in a browser

Built output served by `astro preview`, driven in Chrome at 1280×820.
Screenshots beside this file: `S1.3-latte.png`, `S1.3-mocha.png`.

## The shell

Top bar with the wordmark, the three sections and the toggle; a reading
column at the measure; the footer at the foot of the window on a short page.
Both screenshots show it.

## The two schemes, from the system preference alone

| emulated `prefers-color-scheme` | `--base` | `--text` | `color-scheme` | toggle offers |
|---|---|---|---|---|
| light | `#eff1f5` | `#4c4f69` | `light` | Dark |
| dark  | `#1e1e2e` | `#cdd6f4` | `dark`  | Light |

No `data-theme` attribute was written in either case, and `localStorage` was
empty — an unchosen visitor follows their system through the media query in
`tokens.css`, and the button's label followed the system flip on its own,
which is the `matchMedia` listener in `theme.js` working.

## The toggle, and that the choice sticks

Clicked once under a dark system preference:

```
{ dataTheme: "light", stored: "light", base: "#eff1f5",
  label: "Dark", aria: "Switch to the dark theme" }
```

Reloaded, still under a dark system preference:

```
{ dataTheme: "light", base: "#eff1f5" }
```

The stored choice beat the system preference across a reload. The button
announces what it will do, not what is currently true.

## The CSP hash, which is the one that fails silently

```
{ jsClass: true, dataTheme: "light", ... }
```

`jsClass: true` is the proof: the `is:inline` snippet in `<head>` executed, so
the sha256 in `astro.config.mjs` matches it. A wrong hash fails nothing — not
the typecheck, not the build — and the browser refuses the script with only a
console line. The console carried no CSP violation; the one 404 logged is a
favicon this site does not yet ship.

`test/csp.test.mjs` now recomputes that hash from `Base.astro` on every
`npm run check` and prints the correct value when it disagrees, so the next
person to edit the snippet cannot forget.

## The fonts, and the hashing trap

```
document.fonts → "Source Sans 3-514be13c4afd4c18",
                 "JetBrains Mono-e1c49e55591a93c7", + fallback faces
body font-family → "Source Sans 3-514be13c4afd4c18", …
```

The built family names really are hashed, and the page really is rendering
the downloaded face rather than a fallback.

## What is NOT proven here

The sticky in-page table of contents (`src/components/Toc.astro`,
`src/layouts/Reading.astro`) typechecks and builds, but no page uses a reading
layout yet — the first one arrives with S2.4's worked concept page, and that
is where its rendering should be checked in a browser. Astro's container API
cannot render `.astro` under bare `node --test`; it needs Vite, and adding a
test framework to a site repo is a fleet decision, not this stage's.

"No flash before first paint" rests on the snippet being synchronous in
`<head>` ahead of any painted content, plus the evidence above that it runs.
An attempted `MutationObserver` measurement recorded nothing, because an
init-script at document-start has no `documentElement` to observe yet.
