## The number nobody else publishes: the red gates that never ran

Red-gate exit codes across the whole corpus: `1` × 23, `2` × 1, `3` × 1, and `-1073741502` × 4.

That last one is `0xC0000142` — a Windows crash status from a process that failed to initialise.
Those four rows have recorded durations of 21, 26, 37 and 178 milliseconds against neighbours in the
same run at 8.2s, 52.7s and 672.8s. The check did not fail; it never started. That is the
distinction only a stored exit code can make, and it is the same trap this repo's own tracker warns
about from the other side: a failed Astro build exits `0xC0000409`, not `1`, so a wrapper testing
`exit == 1` calls a crashed build green.

`totalGatesCrashed` is defined in the harvest as a red gate whose exit status is negative or above
128 — a status the command did not choose.

## Distribution, which is the article's second section

Red gates concentrate. Twelve of the eighteen published runs never saw one; the six that did:

| run | red | of |
|---|---|---|
| the-engine-run | 9 | 81 |
| the-terminal-face | 6 | 110 |
| the-ci-cleanup | 5 | 28 |
| the-second-false-start | **4** | **4** |
| the-accounting-run | 3 | 100 |
| the-orchestrator-core | 2 | 96 |

`the-second-false-start` is the article's clean case and the reason the corpus keeps its false
starts: a battery red every time it ran, no checkpoint closed, run abandoned. Both runs named in the
article's evidence strip are published with `gatesRed`, `gatesTotal` and `checkpointsDone` beside
each other, so a reader can see that the run with the most red gates in the corpus is also one that
closed every checkpoint it planned.
