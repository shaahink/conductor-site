## The machinery: a third evidence namespace

The site could say what a *run* cost and what the *corpus* cost. It had no way to say what a run
cost **under one particular ceiling**, and that is the only unit this article can be written in: a
run whose cap moved halfway through has two populations in it, and the average across them is a
number about nothing.

So the harvest now asks `conductor budget <run> --json` once per published run — the fourth source,
and the only one that can see a ceiling at all, because `runs.limits_json` is NULL for every
imported run and no cap can ever be recomputed from SQL here.

| | |
|---|---|
| windows published | **22**, across the 18 runs |
| of them under a measured ceiling | **8** |
| new corpus keys | `cappedWindows`, `sessionsUnderACeiling`, `nudgesDelivered`, `nudgesHonoured`, `killedAtACeiling`, `killedAfterANudge` |
| new per-window keys | `windowCap`, `windowNudge`, `windowFloor`, `windowMedianCloser`, `windowMaxCloser`, `windowNudgeVsFloor`, `windowNudgeVsMedianCloser`, `windowHeadroom`, `windowWrapUp`, `windowHeadroomVsWrapUp`, `windowRollovers`, `windowRolloverRate`, `windowNudged`, `windowNudgesHonoured`, `windowKilledAfterANudge`, `windowSessions`, `windowCostedSessions`, `windowCheckpoints`, `windowTokens`, `windowTokensPerCheckpoint` |

A window key is its run's published label followed by the ceiling it ran under —
`the-long-build-capped-6m`, `the-orchestrator-core-uncapped`. A cap that moves therefore *renames*
the window and any citation of it fails, which is the gate working rather than a typo.

**One rule differs from the run namespace, deliberately.** A run must carry every per-run key or the
corpus is stale. A window need not: a window with no ceiling in force has no nudge, no headroom and
no wrap-up, because nothing was ever asked to wrap up. Zero there would be a measurement, and it is
not one. Both `src/lib/evidence.ts` and the gate in `scripts/harvest.mjs` therefore fail when *no
window a page names* carries a cited key, rather than when *some* window lacks it.

Nine new tests cover the namespace (`test/harvest.test.mjs`): the key shape, the absent cap-shaped
keys on an uncapped window, a capped window nobody ever nudged publishing no wrap-up, a key
collision inside one run, an excluded run taking its windows with it, the corpus ceiling block
counting only capped windows, run-versus-window key disjointness, and every window figure in the
committed corpus naming the verb as its source.

`BUDGET_SHAPED` was widened so the guard still bites on the new names: `/^floor/i` → `/floor/i`, and
`/closer/i` added. Every one of the 20 window keys is budget-shaped by that test, and every one
passes only because `conductor budget` answered it.

## The number nobody else publishes

Across the eight windows in this corpus that ran under a measured ceiling:

| what | measured |
|---|---|
| sessions run under a ceiling | **168** of 340 |
| nudges delivered | **122** |
| nudges honoured — stopped and ended clean | **72** of 122 |
| sessions killed at a ceiling | **50** |
| of those killed, how many had already been nudged | **50 of 50** |

Every session the engine has ever killed at a ceiling had already been asked to stop, in time, and
carried on anyway. The cooperative break converted **none** of the population it exists for. That
identity holds window by window, not only in the total: in all eight capped windows,
`nudged − nudgedAndEndedClean` equals `rollovers` exactly.

## The methodological finding the article is built on

A cap censors its own evidence, and the corpus shows it at both ends of the distribution:

| | measured |
|---|---|
| engine's median closing session, **uncapped** window | **17.5M** |
| engine's median closing session, **8M-capped** window | **7.3M** |
| site repo's floor, **uncapped** window | **6.9M** |
| site repo's floor, **6M-capped** window | **675.8K** |

Same repository, same plan, same kind of work in each pair. The median closer measured inside a
capped window can only count sessions that closed a checkpoint *without hitting the ceiling*; the
floor measured inside a tight one is not a lean session, it is one that died early enough to be
cheap. Hence the article's rule: **you cannot measure a budget from inside the budget.**

## Cost per checkpoint, window by window — the controlled comparison

| window | ceiling | nudge ÷ median closer | rollover rate | tokens per checkpoint |
|---|---|---|---|---|
| the-terminal-face, capped | 8M | 0.84x | 30.3% | 17M |
| the-orchestrator-core, uncapped | — | — | 0% | 19.4M |
| the-accounting-run, capped | 32M | 1.63x | 0% | 16.8M |
| the-long-build, uncapped | — | — | 0% | 13M |
| the-long-build, capped | 6M | 0.85x | 64% | 19.5M |
| the-long-build, capped | 9M | 0.83x | 22.2% | 14.3M |

A cap **below the floor the same repo had just demonstrated** (6M against a measured 6.9M) put cost
per checkpoint *up*, from 13M to 19.5M, and killed close to two thirds of the window's sessions.
Raised to 9M it recovered most of the way but not all — because the nudge was still below that
window's median closer. A cap set *with* headroom (32M, nudge 22.5M, reserve 5.08x the measured
wrap-up) was the cheapest of the engine's three windows and rolled over nothing.

## Corrections to SPEC Part V, article 3

Two figures in the design document are stale and were **not** published as written. Both were true
when the SPEC was authored on 2026-08-06; the accounting run has since grown.

| SPEC says | `conductor budget` says today |
|---|---|
| "zero rollovers in **26** costed sessions" | zero rollovers in **30** costed sessions |
| "the cheapest window of the three at **15.5M** per checkpoint" | **16.8M** per checkpoint |

The SPEC's `25–54M` and `12.8–15.3M` per-checkpoint ranges for the site repo are **stage-level**
hand figures from the pre-verb analysis, not windows. The article publishes the verb's window
numbers instead, per the plan's rule that where a hand query and the verbs disagree, the verbs are
reading the data.

`capPayoff` is deliberately **not** published: the verb only computes it for the three runs whose
ceiling moved (1.556, 1.366, 1.567), and per-run keys must be uniform across all 18 runs. The same
ratio is visible on the page anyway, as two windows' `windowTokensPerCheckpoint` side by side.
