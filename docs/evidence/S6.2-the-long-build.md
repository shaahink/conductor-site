# S6.2 — Report B, the long build

`src/content/reports/the-long-build.yaml`, published at `/runs/the-long-build/`.
1,484 words across seven sections, thirteen evidence keys, one cited run and
three cited budget windows. No figure is typed into prose; the comparisons are
made in words and rendered by the strip from `src/data/corpus.json`.

The checkpoint asks for the shortfall to be the subject rather than a footnote.
It is the standfirst, the first heading, the last heading, and the reason the
report exists.

## The shortfall has a measured cause, and it is not the agent

The store was read read-only (`mode=ro`, `DatabaseSync(..., { readOnly: true })`)
and the budget verb was run against the run id. The run did not have one ceiling
— it had three in succession, and `conductor budget` reconstructs each stretch
of sessions as its own window. All three are in the corpus and all three are on
the page:

| window | sessions | checkpoints | rollover rate | median closing session |
|---|---|---|---|---|
| uncapped | 10 | 10 | 0% | 15.4M |
| capped at 6M | 50 | 15 | 64% | 5.4M |
| capped at 9M | 9 | 5 | 22.2% | 7.7M |

Under no ceiling the run closed a checkpoint per session and nothing was killed.
Under the tightest ceiling it spent five times the sessions to close half as
many checkpoints again, with nearly two-thirds killed at the ceiling. Raising
the ceiling brought the rollover rate down by roughly two-thirds. One variable
moved across those windows — same repository, same plan, same agents, same
gates.

Tokens per checkpoint went **up** under the tight ceiling (13M → 19.5M → 14.3M).
That is the report's central claim and it is the opposite of what a ceiling is
bought for.

The median closing session falling from 15.4M to 5.4M is not an efficiency gain
and the report says so: a session that would have needed longer than the ceiling
allows never closes anything, so it never joins the population of sessions that
closed something. The cap censors its own evidence. Article 3 has the full
working; this report points at it rather than repeating it.

## The arithmetic trap this report had to avoid

The three windows' checkpoint counts sum to 30. `conductor history` says the run
closed 45. **These are different foldings of the same event log and they do not
add up to each other.** The report therefore compares *within* windows only —
rates, ratios and orderings — and never adds a window count to a run count or
divides one window's tokens by another window's checkpoints. That last mistake
is the one the SPEC records as having published a cap benefit of 4.0× that
measured 1.6×.

A third answer exists in the same file: a raw `select count(*) from events where
type = 'CheckpointConfirmed'` returns **9** for this run, against the engine's
45. The report mentions that gap in words, without a figure, because it is the
site's own rule made concrete on the very run it is describing — and because a
system reporting 9 of 46 and a system reporting 45 of 46 would be read as two
different projects.

## Everything else says the run finished

This is the part that makes the report worth publishing. Measured on the same
read-only pass:

- All **nine** stages carry `status = 'done'`. Every stage in the plan was
  confirmed.
- Gates: none red. The run contributed nothing to the corpus red count.
- The final session ended `Advanced` with a commit.
- Bugs: **40 fixed, 1 open**.
- Ledger: 203 entries — 66 notes, 64 findings, 46 decisions, 15 amendments,
  8 traps, 4 observations. One handover per session, all 69.
- Session outcomes: 25 `Advanced`, 8 `Progress`, **34 `RolledOver`**,
  1 `Interrupted`, 1 `NoProgress`.

So the shortfall survives in exactly one number, and only because something
published a denominator. A system reporting checkpoints closed without
checkpoints planned would have shown a clean sheet here without breaking any
rule it had agreed to. The report makes that its second section.

## Anonymisation

- The scenario is reworded from the one in SPEC Part VI, which reads "the run
  that ended at 45 of 46". That string cannot be content: `refuseTypedFigures`
  rejects a two-digit count in prose, and rightly — the count belongs to the
  strip. Published scenario: "A large interactive feature built inside an
  existing site, and the checkpoint that never closed".
- No client, no domain, no private repository name, no stage title. The probe
  script redacted every string field longer than twelve characters before
  printing, so no stage or checkpoint title ever entered this session's context.
- Nothing quoted from field notes; the probe scripts live in the OS temp
  directory and are not in this repository.
- `npm run anonymity` passes over the built output.
